## Errors, deviations, assumptions, workarounds

- `web_extract` returned a DuckDuckGo search-only backend error; Google JavaScript/bot page and DuckDuckGo bot challenge did not yield docs; relied on official GitHub/GitLab sources.
- Python `bs4` not installed; retried searches using Python stdlib (Bing results irrelevant).
- Must deviate from official compose: it would collide with preexisting `quip-validator` and bind disallowed ports, and its standard logging depends on dashboard syslog. Use unique names, bind mounts, Docker json-file logging, local loopback ports only. Do not run vendor Makefile/cron or auto-remove-orphans.
- Current GitHub repo has historical/stale CPU template; use `config/quip-miner.toml` (v0.3) as reference, with keys relocated to `./keys`.
- Upstream deployment calls node a validator but only three genesis authorities have slots. Ours intentionally starts role FULL without `--validator` (no authority/session keys): it syncs/relays and lets a separate miner submit proofs. No claim of becoming a consensus authority.
- Miner image entrypoint ignores PUID/PGID in practice: unconditional `chown -R quip:quip /data` changes `./keys` directory from uid 1003 to 1000 with mode 0700 and secret 0600. `stat` of individual files as host uid 1003 failed Permission denied; read the official image's entrypoint via `docker create devnodeb-image-inspect`, `docker cp ...:/entrypoint.sh data/miner-entrypoint-inspected.sh`, and `docker rm` only that created container to diagnose. No secret content read or printed. `sudo -n true` failed (password required); we do not use sudo. On restart the node key was inaccessible to the validator uid1003 and the node exited; durable fix: run both of OUR images as uid1000 (validator honors PUID, miner already uses 1000). Node key and signer remain 0600 in `./keys`. For host editing of config/backup after stopping, a *scoped* temporary root container may restore ownership of only `./keys` (document if used); miner resumes uid1000 on next start.
- Warp sync is advertised in validator `--help` but unusable here: on partially synced DB it reverts then panics, on a fresh DB it panics immediately. Do not enable. Full sync from genesis is the verified working route, though slower. No vendor issue filed (user forbade public posts).
- Upstream expects publicly reachable validator p2p `30333/tcp+udp`; per request host publish is instead only `127.0.0.1:31201` (container's fixed internal 30333), which cannot accept inbound internet peers. The vendor dashboard ports 80/443 are already occupied by other services and disallowed by this task; no dashboard is started. Vendor also recommends public API port 20049, not exposed. Need explicit authorization for external ingress; no firewall was changed. Miner descriptor has `public_host="127.0.0.1"`, `public_port=31200` as local-only placeholders; vendor filed that descriptor on testnet, but it is NOT externally dialable and must not be described as public reachability.
- The 404 on faucet GET `/api/faucet/health` was only a path mismatch: GET `/health` returned OK, and subsequent automatic funding succeeded on Aglais. Normal Docker daemon metadata/log files live in Docker's managed storage; all bind-mounted node/miner persistent data and keys are project-local, with no named volume created.
- Vendor nodes README names topology `0xe66d3dfa…` (4577/41515), but the live runtime 118 mining snapshot downloaded topology `0xcbec1eb4e9dc…` (4577/41514). We used the live chain snapshot, did not seed topology or override it. Docs would be clearer if they tracked current runtime and described how to check it.
