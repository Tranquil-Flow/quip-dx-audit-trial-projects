# RESULT

## Status: WORKING

A fresh Quip Network CPU miner was registered against the live Aglais
testnet, funded by the public faucet, filed a node descriptor, and ran
SA sampling work against the chain's current quantum block. The container
was stopped at the end with no foreign resource touched.

## How to run

    cd /private/tmp/devtrials3/t05-minimax-m3
    docker compose -p t05-quipdev pull             # refresh image
    docker compose -p t05-quipdev up -d            # start
    docker compose -p t05-quipdev logs -f          # follow logs

    # check
    curl -s http://127.0.0.1:8086/healthz
    curl -s http://127.0.0.1:8086/api/v1/status | python3 -m json.tool

    # stop
    docker compose -p t05-quipdev down

The full ops runbook is in `RUNBOOK.md`.

## What was built

- `docker-compose.yml` — single `miner` service, project `t05-quipdev`,
  container `t05-quip-cpu`, loopback-bound port 8086 only.
- `config/quip-miner.toml` — v0.3 first-run template pointed at the
  pre-existing `quip-validator` over `host.docker.internal:9944`.
- `.env` — pins `QUIP_MINER_TAG=stable`.
- `data/keystore.json` (mode 600) — H4 hybrid sr25519 + FN-DSA-512 key
  generated on first boot. Backed up to `keys/keystore.json`.
- `data/config.toml` — live config (generated by entrypoint from the
  mounted template).
- `data/attempts/8036/attempts.jsonl` — 11 real SA attempts.
- `evidence/` — snapshots of status / stats / healthz / attempts / logs.

## What did NOT work

1. **No winning proof.** Expected — 1 CPU at the current target
   (-14697 milli) against a 4577-node Advantage2 topology is well
   below steady-state solve rate. The work pipeline is verified
   end-to-end (11 attempts dispatched, results received from the miner
   binary, stash updated each time) but the lottery didn't pay out in
   the 70-second observation window. The miner is still running
   probabilistically — it just needs more time, or a higher CPU budget.
2. **Could not query chain storage directly.** The pre-existing
   `quip-validator` runs with `--rpc-methods=safe` so `state_getStorage`
   is blocked to external callers (`error: RPC call is unsafe to be
   called externally`). I deliberately did not touch that container.
   Evidence of registration comes from the miner's own logs and REST
   surface (`registered this account as a miner on chain`, `filed node
   descriptor`, `miner_registered=true`, `registered_at=375443`).
3. **Runtime spec mismatch.** README says Aglais is runtime spec 117;
   live spec_version returned by `chain_preflight` is **118**. Means the
   validator chain spec in `chain-specs/aglais-network.json` was current
   at the 2026-09-02 Aglais genesis but the runtime has been bumped
   once since. Doesn't affect this miner (quantum_pow_api=2 unchanged),
   but it means the `CHANNEL=stable` image I pinned may not exactly
   match the spec file in the repo. Inconclusive without storage reads.

## What in the vendor's docs/tools would have made this easier

1. **Document the "miner-only" topology** as a first-class option.
   The README walks through `make testnet` (which bundles validator +
   miner + dashboard) but the `QUIP_VALIDATOR_RPC_URLS` env var on the
   dashboard service is the only place it mentions pointing at a remote
   validator. A `make miner-only` target or a one-liner "if you already
   have a substrate validator, point `validators = [...]` at its WS URL
   and skip the local one" would have saved guessing on the config.
2. **Tag list access.** `curl https://registry.gitlab.com/v2/.../tags/list`
   returns 401 Unauthorized without auth, even for public images. Pull
   `latest`, `beta`, `stable` individually to compare SHAs is workable
   but not friendly. A `quip` CLI subcommand like `quip miner tags
   --channel=beta --since=7d` would be a clear win.
3. **Make `public_host` validation friendlier.** The coordinator exits 64
   on empty `public_host` but only because the schema says "is not a
   host." A useful operator log would be the exact offending key + value
   rather than a generic exit. (Also: allow `public_host = ""` for miner-
   only setups where the descriptor is filed empty on purpose.)
4. **Published chain spec at runtime spec 118.** The README and the
   `chain-specs/aglais-network.json` file say 117; the running network
   is 118. Either the chain spec file needs an update or the README is
   stale. Without storage reads it's impossible to tell which without
   bringing up a second validator, which is exactly what the docs steer
   you away from.
5. **Tag the v0.3 Aglais line explicitly.** The README warns that
   `latest` is pre-Aglais and "is not a release pointer — do not name
   it." The only release tags I could find by trial-and-error were
   `beta` and `stable`, both of which point at moving Aglais lines.
   No `v0.3.1` / `v0.3.1-rc4` literal tag — even though
   `data/config.cpu.toml`'s sibling file references `quip-miner
   v0.3.1-rc3-aglais-prerelease` in a comment, the registry has no such
   tag. Pinning a release build requires keeping a SHA in `.env`.
6. **A `node-cli` / `quipctl` for reading chain state.** The only
   way to confirm "yes, my miner is on-chain" from outside a validator
   is to either enable unsafe RPC on that validator (which I won't do
   to one I don't own) or to read it from the miner's REST surface.
   The `/api/v1/status` route is great but it's local to my own miner —
   I can't use it to query another operator's account. A standalone
   `quipctl miner show --account 5H36...` against any public RPC URL
   (with `--allow-insecure`) would be the right tool.
7. **`/api/v1/mining/attempts` parameter contract.** Returns 400 with
   `supply ?solution_number=N` but `?qblock_id=8036` alone also returns
   400. The endpoint only accepts `?qblock_id=X&solution_number=N`. The
   doc string at the top of `config.example.toml` lists both `qblock_id`
   and `solution_number` as implicit, but a one-line spec for the
   handler would prevent the trial-and-error.
8. **Add a `make miner-only` / `make solo` target.** The Makefile has
   `testnet`, `localdev`, `pull`, `down`, `logs`, `clean`. A miner-only
   target would `docker run` the cpu/cuda image with `--network host`
   and `validators = [ws://host.docker.internal:9944]` baked in, no
   compose project needed.
